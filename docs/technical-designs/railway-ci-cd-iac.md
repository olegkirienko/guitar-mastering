## GitHub validation and branch policy

Add `push: { branches: [main] }` to the existing `Validate` workflow and remove `workflow_dispatch`. Retain `pull_request`, the single `validate` job, all validation commands, PostgreSQL service, and minimal permissions. Do not add branch/path filters to the `push` event or job-level `if` conditions. `pull_request` checks the PR merge candidate before merge; a merge, squash, or rebase can create a different SHA, so the `push` event validates the actual `main` commit Railway must deploy. Record `github.sha` and the workflow run URL for acceptance.

Leave `Validate` without workflow/job concurrency, including after adding `push`. GitHub's default allows runs in parallel. A concurrency group can cancel pending runs even with `cancel-in-progress: false`, and Railway's cancelled-run rule can allow another successful workflow to mask the cancellation ([GitHub syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [Railway autodeploys](https://docs.railway.com/deployments/github-autodeploys)). If resource pressure later demands serialization, design and review a mechanism that preserves every `main` commit's validation conclusion; do not add it implicitly here.

### Exact-SHA promotion guard (HIGH-01)

Before enabling production GitHub autodeploy, put a small TypeScript/Node verifier at the **start** of Railway pre-deploy, followed by `pnpm db:migrate` only on verifier success. Implement it in `server/verify-ci.ts`, which the existing `tsconfig.server.build.json` compiles to `dist-server/verify-ci.js`; add a `release:predeploy` package script with the exact command `node dist-server/verify-ci.js && pnpm db:migrate`, and set Railway's effective pre-deploy command to `pnpm release:predeploy`. Verify the built image contains that JavaScript file and package script. The verifier uses `RAILWAY_GIT_COMMIT_SHA` and a pinned `olegkirienko/guitar-mastering` repository and `.github/workflows/ci.yml` identity to query the GitHub Actions API. It requires a completed `success` workflow run with `event: push`, `head_branch: main`, and `head_sha` equal to the full deployment SHA. It then requires the single `validate` job and each named validation step (install, lint, unit, browser, PostgreSQL, build) to have `success` conclusions. It rejects absent or malformed SHA, no matching run, skipped/neutral/cancelled/failing jobs or steps, API errors, pagination uncertainty, and timeouts. Test the parser with representative API fixtures and a live read-only call before enabling. The guard must have a short bounded timeout and a clear nonsecret diagnostic. If GitHub cannot be reached, the new deployment fails before migration and startup. The exact bootstrap order and production proof are specified below.

Set a Railway production variable `GITHUB_CI_GATE_REQUIRED=true` before source connection. With this flag, the verifier rejects deployments without Railway Git SHA metadata, including manual CLI releases; emergency manual release requires a separately approved, time-bounded flag change and read-back. The old healthy deployment remains serving while a new pre-deploy fails. Only GitHub-triggered commits are within the automated release invariant. Railway may still fetch and build a SHA before the verifier runs, so the preventive guarantee is **no migration, startup, or promotion without the exact successful push validation**; the target sequence's strict “CI before build” property remains dependent on Railway Wait for CI semantics. The design-approval gate must explicitly accept that residual build risk; otherwise keep autodeploy disabled and choose a different deployment architecture. A commit that modifies the verifier or workflow needs human review under branch rules.

### GitHub API credential amendment approved (MEDIUM-02)

The 2026-09-22 read-only comparison proved that the public repository's pinned workflow-runs and jobs endpoints work both anonymously and with authentication. A normal verification costs two core requests and may use at most one bounded retry per endpoint, for no more than four requests per candidate deployment. The operational envelope is at most ten candidate deployments per hour. Although this fits the nominal anonymous 60/hour limit, GitHub accounts anonymous requests by source IP and Railway egress isolation is not guaranteed; unrelated traffic could exhaust the budget. Authenticated calls showed a 5,000/hour budget, so approved [Design Amendment 02](../reviews/railway-ci-cd-iac/design-amendment-02-verifier-credential.md) selects authenticated access as the least-privileged reliable mode.

After approval, use a fine-grained owner token restricted to `olegkirienko/guitar-mastering`, repository `Actions: read`, unavoidable metadata read, no write access, and at most 90-day expiry. Store it only as the sealed production-web-service `GITHUB_ACTIONS_READ_TOKEN`; IaC may preserve the reference but never the value. The verifier must not fall back anonymously. It permits one workflow-runs call filtered by the full deployment `head_sha`, `branch=main`, and `event=push`, followed by one jobs call for the selected run. Both request `per_page=100`, reject count/array or next-page uncertainty, and allow at most one retry only for a transient network error or `5xx`. The verifier fails before migration on `401`, `403`, `429`, any other non-`200`, timeout, malformed JSON or rate-limit metadata, pagination uncertainty, unexpected redirect, or fewer than 100 authenticated core requests remaining. Never log the token or authorization header. Rotate at least seven days before expiry through a separately reviewed variable action, prove the replacement from the deployed image before revoking the old token, and revoke immediately on suspected disclosure while keeping autodeploy disabled until a reviewed replacement passes.

Before enabling Wait for CI, inventory enabled GitHub Actions workflows, reusable calls, and GitHub Apps producing checks on `main`. Keep `Validate` as the sole success-producing Actions workflow on production commits, or document every additional one and prove it cannot mask a cancelled `Validate`. Remove `workflow_dispatch` from `Validate`; a manual rerun or dispatch is not accepted as the required push run. A separate diagnostic workflow may be designed later, but it must not create a successful check suite on the deployment SHA while Wait for CI is active. Audit workflow triggers and branch rules again before every release-policy change. Disallow CI skip directives in PR title, commit subjects, merge/squash messages, and release procedure; require the unskipped post-merge push run in the guard. GitHub can still omit that run after a skip directive, and Railway may proceed on a skipped/neutral or masked cancelled result; the guard then rejects it. A successful push workflow with skipped required steps also fails the guard. Branch protection alone cannot prevent those cases ([GitHub skip rules](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs), [Railway Wait for CI](https://docs.railway.com/deployments/github-autodeploys)).

Desired active `main` ruleset or equivalent branch protection: require PRs (at least one human approval and resolved conversations, subject to repository ownership capability), require the unique `validate` GitHub Actions check from `Validate`, prohibit force push/deletion, restrict or eliminate direct push and admin bypass where the repository plan permits, and prevent workflow-file edits from bypassing review. Check current repository ownership and plan features before choosing the exact settings. Require current branch state before merge or use merge queue only with a separately verified `merge_group` trigger; merge queue is outside this slice. Manual workflow runs cannot substitute for the required `main` push run. Document that GitHub's required-check policy guards merge while Railway Wait for CI controls build timing and the pre-deploy verifier guards migration and promotion; acceptance correlates SHAs and run conclusions.

### Restart-policy platform exception and parity rule

Railway documents `ON_FAILURE` as the effective default. After the reviewed production IaC apply, the active deployment and service instance report `ON_FAILURE` with `restartPolicyMaxRetries = 3`, but fresh raw configuration reads omit `restartPolicyType`. Railway IaC is stateless, and SDK 3.11.0 accepts the explicit field in the desired graph; nevertheless, a fresh plan repeatedly proposes `restartPolicyType: null → "ON_FAILURE"`. The explicit default does not round-trip through the current raw/IaC state model. This is a Railway platform exception, not proof that the effective restart behavior is wrong.

The IaC source shall omit `deploy.restartPolicyType` and continue to manage `deploy.restartPolicyMaxRetries: 3`. For this project, parity means a clean IaC plan for every supported round-trippable field, together with documented platform exceptions validated by runtime/read-only checks. After each deployment, read the effective service/deployment restart policy and require type `ON_FAILURE` and maximum retries `3`; stop acceptance and investigate if either differs or cannot be verified. Record the exception and the check alongside the plan. If Railway later exposes `restartPolicyType` as stable round-trippable state, a reviewed design and IaC change may restore explicit management.

The IaC source may need to represent the existing PostgreSQL resource because a whole-project graph can treat omitted owned resources as deletion. Use the importer/preview and plan to establish ownership semantics. Do not claim a no-op plan is possible until the Config as Code association is cleared. Any inability to preserve effective healthcheck or restart behavior is a design-review blocker for the migration; the restart type exception above requires its own read-only proof. Generated domains are omitted by Railway's importer; preserve and read back the existing domain rather than recreating it.

IaC drift detection: an operator runs `railway config plan --detailed-exit-code` against the pinned production target during a reviewed maintenance check and before every proposed IaC apply; `0` means no drift in supported round-trippable fields, `2` means pending changes, other nonzero is an error. The restart-type exception needs the separate effective-policy check above. Capture redacted output only. Infrastructure changes require a reviewed PR changing `.railway/railway.ts`, explicit operator approval of the exact plan, then a manual `config apply` with fresh read-back. A stale plan or unexpected resource deletion stops the operation. Do not wire `config apply` into `Validate` or an unconditional `main` push workflow. Normal `main` commits only drive application autodeploy.

Rollback before IaC apply: restore the previous Railway Config File association and keep `railway.json`, verify the previous production deployment and readiness. Rollback after apply: use a reviewed inverse IaC change or restore the previous settings/association from the captured snapshot; re-plan and read back identities and behavior. If an app deploy occurs during a bad configuration window, disable autodeploy and restore the prior migration-compatible deployment. Never restore the production database or recreate PostgreSQL merely to reverse IaC configuration.
